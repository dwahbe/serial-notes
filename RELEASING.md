# Releasing Serial Notes

How a release is cut, signed, shipped, and auto-updated. Day-to-day build/dev-loop docs live in [CLAUDE.md](CLAUDE.md) → Build & Run.

```bash
./scripts/release.sh 0.2.0   # validate clean tree + smoke-build + tag + push → CI publishes
```

Pushing a `vX.Y.Z` tag triggers `.github/workflows/release.yml`: build → Developer ID sign → notarize → staple → GitHub Release → Sparkle `sign_update` → appcast commit. `release.sh` only validates + tags + pushes (build/notarize locally only to *test* — never publish locally, the tag already does it).

- **`release.sh` refuses to tag if HEAD == the last tag's commit** — `CFBundleVersion` is the commit count and Sparkle upgrades by it, so an unchanged build number means installed users never get offered the update.
- **Version source of truth = the git tag.** `build-app.sh` stamps `CFBundleShortVersionString` (from the tag) + `CFBundleVersion` (commit count) via `PlistBuddy` before signing; CI's `MARKETING_VERSION` wins over the tag lookup. `Info.plist` versions are fallbacks for non-git builds only.
- **Versioning:** SemVer; stay on `0.x.y` for beta — major `0` *is* the beta signal (Settings → About shows "(beta)"; CI titles the release `vX.Y.Z (beta)`). Beta ships as a **full release, not a pre-release**, so `/releases/latest` + the site link resolve. Bump to `1.0.0` to drop it.
- **Distribution:** stable-named `SerialNotes.dmg` (site links `…/releases/latest/download/SerialNotes.dmg`) while the per-tag download URL stays unique for the appcast. `make-dmg.sh` builds a styled drag-to-Applications DMG with only `hdiutil` + Finder AppleScript (no deps); styling degrades to a plain DMG if automation is denied.
- **Signing:** Developer ID + hardened runtime + secure timestamp; both `.app` (via a throwaway zip) and `.dmg` are notarized + stapled (Gatekeeper checks the downloaded image). `build-app.sh` embeds + signs `Sparkle.framework` **inside-out — helpers first, then the framework, then the app** (a stray helper signature breaks notarization). **Ad-hoc dev builds skip hardened runtime** (`--options runtime` only for a real identity): otherwise library validation kills the ad-hoc app at launch for loading the team-less ad-hoc Sparkle framework; release builds are safe because app + framework share one Developer ID team.
- **Auto-updates (Sparkle):** each DMG is EdDSA-signed (`sign_update`); `update_appcast.py` inserts the item newest-first and is **idempotent** (re-running a version replaces its item, not duplicates), and CI commits `appcast.xml` to `main`. Sparkle upgrades by the highest `sparkle:version`, not feed order. Appcast items intentionally omit `<description>` and `sparkle:releaseNotesLink`, so Sparkle shows only the compact "update available" prompt instead of a changelog pane. `SUFeedURL` + `SUPublicEDKey` live in `Info.plist`; the EdDSA private key is in the keychain + a CI secret (`generate_keys -x`). **`SUFeedURL` points at the site's counting proxy** (`https://serialnotes.app/appcast.xml` → `site/src/pages/appcast.xml.ts`), which serves a byte-faithful copy of the repo-committed appcast and tallies each Sparkle check as an anonymous active-install count (UTC day + version only; non-Sparkle user agents aren't counted). The repo-committed `appcast.xml` stays the source of truth **and** the live feed for pre-0.1.7 installs — never remove or break the raw-GitHub copy, and deploy site changes before tagging a release that depends on them. Counting is best-effort: a Supabase failure must never break the feed response.
- **Install location.** A quarantined app run from `~/Downloads` is **App-Translocated** to a read-only mount and can never self-update. The DMG's drag-to-Applications layout is the primary nudge (its background spells out the second step — "then open it from your Applications folder"); `MoveToApplications.moveIfNeeded()` (first call in `applicationDidFinishLaunching`) is the backstop — when not already in an Applications folder it relocates into `/Applications` (true source resolved via `SecTranslocate*` dlsym'd from Security; authenticated `ditto` only if a plain copy is denied) and relaunches, then `exit()`s. **A read-only source (the mounted DMG) installs silently** — double-click-in-DMG is a one-action install, and the first-run guide opens on the relaunched copy; a writable source (`~/Downloads`) still gets the move prompt. No-ops for dev builds, tests, and after the user declines once (the declined flag gates only the prompt path, never the DMG auto-install).
- **Release notes**: CI publishes with `--generate-notes` (PRs grouped by label per `.github/release.yml`), but that output is a placeholder — after the release lands, replace it via `gh release edit vX.Y.Z --notes-file …` with hand-written notes in the house style below. No `CHANGELOG.md` — the Releases page is the changelog.
- **Release-notes house style** (see v0.2.2 onward for the pattern):
  - **Shape:** one summary line, then a flat list of ~5–7 `**bold benefit phrase** — prose` bullets (1–3 sentences each, user-benefit voice, fixes woven in — no "Fixes" section), ending with a lowercase `**Full changelog**: <compare link>`.
  - **Plain over clever, everywhere.** Both the summary line and the bold phrases describe the change literally — no hooks, wordplay, or cuteness ("It looks after itself" → "Keeps working if the page is deleted"), and no personality flourishes ("Sorry about that one.").
  - **Describe, don't oversell.** A phrasing that reads bigger than the change is wrong even if catchier: "Improvements to the notepad's Markdown rendering." beat "The notepad now renders your Markdown as you type it." because the latter overstated what shipped.
- **CI secrets** (Settings → Secrets and variables → Actions): `BUILD_CERTIFICATE_BASE64`, `P12_PASSWORD`, `KEYCHAIN_PASSWORD`, `NOTARY_API_KEY_BASE64`, `NOTARY_KEY_ID`, `NOTARY_ISSUER_ID`, `SPARKLE_ED_PRIVATE_KEY_BASE64`.
